# RP2040 베어메탈

부품 기준 문서: [parts/xiao-rp2040.md](../parts/xiao-rp2040.md)
최종 갱신: 2026-09-09

## 무엇인가

Pico SDK를 링크하지 않고 레지스터를 직접 다루는 펌웨어다. 목적은 학습이다.

산출물은 플래시가 아니라 SRAM에 올린다. boot2와 XIP를 뒤로 미뤄, 실패했을 때
의심할 대상을 이 코드 하나로 좁히기 위해서다.

## 구성

| 파일 | 내용 |
|---|---|
| `ld/ram.ld` | SRAM `0x20000000` 배치. 벡터 테이블 맨 앞, bss 맨 뒤 |
| `src/start.S` | 벡터 테이블 두 워드와 리셋 핸들러 |
| `src/main.c` | 현재 단계의 본체 |
| `src/clock.[ch]` | XOSC 기동과 PLL_SYS 125MHz 전환 |
| `src/uart.[ch]` | UART0 초기화와 문자열 출력 |
| `Makefile` | 빌드 4단계와 check, dump, load, clean |
| `reference/` | 읽기용 참고 자료. SDK 의 boot2 소스와 출처·라이선스 |

## 빌드

빌드는 Ubuntu에서 한다. 호스트 도구는 `arm-none-eabi-gcc`와 `picotool`이다.
Windows 데스크톱의 WSL에는 둘 다 없고 보드도 그쪽에 연결하지 않는다.
갖춰진 버전은 부품 기준 문서에 있다.

| 명령 | 하는 일 |
|---|---|
| `make` | uf2까지 만든다 |
| `make check` | 산출물이 실행 가능한 모양인지 확인한다 |
| `make dump` | 역어셈블을 본다 |
| `make load` | 보드에 올리고 실행한다. 부트로더 모드여야 한다 |
| `make clean` | 산출물을 지운다 |

`build/`는 저장소에 넣지 않는다.

## 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| 0 | 빌드 파이프라인. uf2 생성과 SRAM 적재 | 완료 |
| 1 | GPIO 직접 제어로 LED 깜빡이기. 두 핀 교대까지 | 완료 |
| 2 | 클럭. XOSC 와 PLL 로 125MHz | 완료 |
| 3 | UART. 문자열 출력 | 완료 |
| 4 | boot2. 플래시에서 부팅 | 미착수. USB를 뽑았다 꽂아도 UART 출력이 다시 나오면 통과 |
| 5 | 타이머와 인터럽트 | 미착수. 알람 인터럽트 핸들러가 LED를 1초 주기로 토글하고, UART로 찍은 타이머 값이 벽시계와 맞으면 통과 |
| 6 | 코어1 | 미착수. 코어1이 코어0과 독립으로 LED 하나를 굴리고 UART에 자기 코어 번호를 찍으면 통과 |
| 7 | PIO. GPIO12의 WS2812 | 미착수. 코드에서 정한 색이 WS2812에 나오면 통과 |

4단계부터는 산출물이 플래시에 들어가 공장 펌웨어를 덮어쓴다. 되돌리기는
[backups/xiao-rp2040/](../backups/xiao-rp2040/)의 복구 절차로 한다. 부트로더는 ROM에
있어 어떤 펌웨어를 구워도 B 버튼으로 들어간다.

### 4단계 계획 (문서 기준)

아직 안 했다. 아래는 데이터시트와 boot2 소스에서 읽은 것이고 실물에서 확인되면
"4단계에서 확인한 것"으로 옮긴다.

부트롬은 플래시 맨 앞 256바이트를 SRAM으로 퍼와 마지막 4바이트의 CRC32를 검사하고
실행한다. CRC 규격은 백업 폴더의 `verify.py`가 이미 구현한 것과 같다. 시드
`0xffffffff`, 비트반전, 앞 252바이트. boot2는 SSI를 XIP로 세운 뒤 `0x10000100`에서
스택 포인터와 리셋 벡터를 읽어 뛴다. 따라서 이미지 배치는 이렇다.

| 오프셋 | 내용 |
|---|---|
| `0x10000000` | boot2 256바이트. `reference/boot2_w25q080.S`를 조립하고 252바이트로 채운 뒤 CRC를 붙인다 |
| `0x10000100` | 벡터 테이블. 지금은 두 워드지만 5단계에서 늘어난다 |
| 그 뒤 | `.text`, `.rodata`. 그리고 `.data`의 초기값 |

SRAM 빌드와 달라지는 것은 셋이다.

- 링커 스크립트가 하나 더 생긴다. `.text`는 플래시 주소(VMA)에 두고 `.data`는
  SRAM 주소로 두되 초기값은 플래시에 둔다(LMA). 지금 `ram.ld`는 이 구분이 없다.
- 리셋 핸들러가 `.data`를 플래시에서 SRAM으로 복사하고 `.bss`를 0으로 채워야
  한다. SRAM 빌드에서는 적재기가 대신 해줬다.
- XOSC 기동 코드가 처음으로 일을 한다. 플래시 부팅 경로에서는 부트롬이 USB를
  돌리지 않아 XOSC가 꺼진 채로 넘어온다. 2단계 문서에 예고한 대로다.

이 셋을 한 번에 굽고 전원 순환 하나로 판정하면, 안 떴을 때 boot2와 링커 스크립트와
복사 루틴과 XOSC 기동을 동시에 의심하게 된다. 그래서 세 조각으로 나눈다.

| 조각 | 하는 일 | 통과 조건 |
|---|---|---|
| 4a | boot2 256바이트 생성 | 칩에 굽지 않는다. `factory-flash.bin`의 앞 256바이트와 바이트 단위로 같으면 통과 |
| 4b | 플래시 링커 스크립트와 `.data` 복사·`.bss` 클리어 | 초기값 있는 전역과 없는 전역을 UART로 찍어 둘 다 맞으면 통과 |
| 4c | 플래시에 굽고 실행 | USB를 뽑았다 꽂아도 UART에 문자열이 나오면 통과 |

4c의 통과 조건이 플래시 부팅의 증거인 것은 SRAM 빌드가 전원이 끊기면 사라지기
때문이다. 지금 빌드로는 이 시험을 통과할 수 없다.

4b의 판정 수단은 코드보다 먼저 만든다. 지금 `main.c`에는 전역 변수가 없어 `.data`와
`.bss`가 비어 있고, 복사 루틴을 틀리게 써도 증상이 나오지 않는다. 전역을 쓰는
5단계에 가서야 드러난다.

boot2의 CRC를 붙이는 방법은 둘이다. `verify.py`의 CRC 함수를 재사용해 붙이거나,
`~/opt/pico-sdk/src/rp2040/boot_stage2/pad_checksum`을 쓴다. 전자는 이 저장소 안에서
닫히고 후자는 SDK가 만든 것과 바이트 대조가 된다. 첫 시도는 후자로 하고 통과하면
전자로 바꿔 두 결과가 같은지 본다.

적재는 `picotool load`에 `-x`를 빼고 한다. uf2 목적지가 `0x10000000`이면 부트로더가
플래시에 쓴다. 실행은 리셋 버튼이나 `picotool reboot`.

4c에서 막혔을 때 갈라 볼 것. boot2는 4a에서 걸러지므로 LED도 UART도 없으면 XOSC
기동을 먼저 의심한다. 그래도 안 갈리면 boot2 256바이트를 `factory-flash.bin`의 앞
256바이트로 바꿔 끼운다. 공장 boot2는 검증된 것이다.

### 5~7단계에서 다룰 것 (문서 기준)

- 5단계. TIMER는 clk_ref에서 1 µs 틱을 만든다. 틱 생성은 WATCHDOG의 TICK 레지스터가
  맡으므로 그것을 켜야 타이머가 돈다. ALARM0에 목표 시각을 쓰고 INTE를 세우고
  NVIC에서 IRQ 0을 켠다. 벡터 테이블이 16개 예외와 IRQ 자리까지 늘어난다.
  타이머 틱이 XOSC 기준이라 여기서 처음으로 절대 시간 기준이 생기고, 2단계에서
  못 잰 clk_sys 절대 주파수를 지연 루프 대 타이머 비교로 잴 수 있다.
- 6단계. 코어1은 리셋 후 부트롬 안에서 SIO FIFO를 기다린다. 코어0이 정해진 순서로
  0, 0, 1, 벡터 테이블 주소, 스택 포인터, 진입점을 보내고 매번 에코를 확인한다.
  UART를 두 코어가 같이 쓰면 글자가 섞이므로 SIO 스핀락으로 감싼다.
- 7단계. PIO 프로그램은 어셈블러 산출물이 16비트 명령 배열이다. pioasm을 쓰지 않고
  손으로 인코딩하면 명령 형식을 배우게 되고, 틀리면 SDK의 ws2812 예제 산출물과 대조한다.

### 0단계에서 확인한 것

- uf2 목적지 `0x20000000`, family id `0xe48bff56`
- 벡터 0번 `0x20042000`, 1번 `0x20000009`, `_start`는 `0x20000008`
- `picotool load -x`로 적재하면 부트로더가 USB를 놓는다

링크 단계 검사 두 개를 넣었다. 벡터 테이블이 이미지에서 빠지는 사고와 심볼 주소에
Thumb 비트가 섞이는 사고를 잡는다. 둘 다 빌드는 통과하고 칩에서만 죽는 종류라,
일부러 깨뜨려 차단되는 것까지 확인했다.

### 1단계에서 확인한 것

- RESETS로 IO_BANK0을 깨우고 RESET_DONE 폴링으로 해제 완료를 기다린다
- GPIO CTRL의 FUNCSEL을 SIO(5)로 두고 OE_SET으로 출력 방향을 연다
- OUT_XOR는 마스크에 든 비트를 뒤집는다. 현재 값을 읽을 필요가 없다
- 코드가 의도대로 돈다. `start.S`가 세운 스택도 실제로 쓰인다. 지연 루프가 스택에 카운터를 올린다
- `volatile`이 두 곳에서 필수다. 레지스터 접근에서 빼면 중복으로 보이는 쓰기가 지워진다
- 지연 루프 변수에서 `volatile`을 빼면 루프가 통째로 사라진다. 둘 다 역어셈블로 확인했다

IO_BANK0은 핀마다 STATUS와 CTRL 두 레지스터를 8바이트씩 차지한다.
GPIO n의 CTRL 오프셋은 `0x04 + n*8`이다.

LED 핀 배정과 판정 방법은 부품 기준 문서의 온보드 LED 절에 있다.
켜짐으로는 판정할 수 없다. 풀다운 때문에 코드 없이도 LED가 희미하게 켜진다.

### 2단계 시작 시점에 확인한 것

`picotool load -x` 로 들어오면 부트롬이 USB 를 돌린 뒤 우리 코드로 넘어온다.
그 시점의 클럭 상태를 레지스터에서 읽어 LED 로 표시해 확인했다. 두 번 재현했다.

- XOSC 는 이미 떠 있다. `XOSC_STATUS` 의 STABLE 이 서 있다
- clk_sys 는 ROSC 에서 온다. `CLK_SYS_SELECTED` 는 clk_ref 를,
  `CLK_REF_SELECTED` 는 ROSC 를 가리킨다

USB 는 clk_usb 만 48MHz 면 되고 PLL_USB 의 기준 입력은 XOSC 에서 직접 따간다.
clk_ref 와 clk_sys 를 리셋 상태로 두어도 USB 가 도는 이유다.

여기서 두 가지가 따라온다. 125MHz 로 올리면 clk_sys 가 약 19배가 되므로 깜빡임
속도만으로 판정할 수 있다. 그리고 XOSC 기동 코드는 이 경로에서 이미 떠 있는
XOSC 를 만나 폴링이 즉시 통과하므로 검증되지 않는다. 플래시 부팅으로 옮기는
4단계에서 처음 일을 한다.

판독에는 LED 로 레지스터 값을 뿌리는 임시 코드를 썼다. 3단계에서 UART 가
붙어 역할이 끝나 지웠다.

### 2단계에서 확인한 것

clk_sys 의 출처를 ROSC 에서 PLL_SYS 로 옮겼다. `CLK_SYS_SELECTED` 를 읽어
확인했다.

- 요청 레지스터와 완료 레지스터가 짝인 자리가 셋이다. RESETS 의 RESET 과
  RESET_DONE, 클럭 mux 의 CTRL 과 SELECTED, PLL 의 LOCK
- SELECTED 는 원핫이라 SRC 값이 아니라 `1 << SRC` 와 비교한다
- PLL 의 PWR 은 PD 계열이라 0 이 켜짐이다. 비트를 내려서 전원을 넣는다
- POSTDIV 는 LOCK 이 걸린 뒤에 설정한다. 값을 먼저 정하고 전원을 나중에 넣는다

절대 주파수는 이 단계에서 재지 않았다. 지연 상수를 10배 키웠을 때 체감 속도가
비슷했으므로 대략 10배 빨라진 것과 앞뒤가 맞는다는 정황까지였다. 3단계에서 UART
글자가 깨끗하게 읽히면서 확증됐다.

### 3단계에서 확인한 것

`uart_init` 은 clk_peri 켜기, UART0 리셋 해제, GPIO0·1 을 F2 로 배정, 분주값과
프레임 형식 설정 순으로 간다.

- IBRD 와 FBRD 에 쓴 값은 LCR_H 를 쓸 때 함께 반영된다. LCR_H 를 먼저 쓰면
  분주값이 걸리지 않아 엉뚱한 보드레이트로 나간다
- 핀 방향은 UART 블록이 잡는다. SIO 로 쓸 때와 달리 OE 를 건드리지 않는다
- 송신은 FR 의 TXFF 를 폴링한다. 요청과 완료가 나뉜 형태가 이 트랙에서 네 번째다
- clk_peri 는 리셋값 AUXSRC 가 clk_sys 라 ENABLE 만 세우면 125MHz 가 들어온다.
  glitchless mux 가 아니라서 SELECTED 폴링이 없다

1 Mbaud 로 동작을 확인했다. 125MHz 에서 IBRD 7, FBRD 52 면 계산상 오차가 없다.
Raspberry Pi Debug Probe 의 UART 브리지와 짧은 점퍼선 기준이고, 배선을 길게
바꾸거나 브레드보드를 거치면 다시 확인해야 한다. 115200 도 같은 배선에서
확인했고 그쪽 오차는 0.006% 다.

글자가 깨끗하게 나온다는 것이 clk_peri 가 125MHz 라는 뜻이다. UART 허용 오차는
상대값이라 보드레이트를 올려도 클럭 검증이 더 엄격해지지는 않는다. 1 Mbaud 가
추가로 시험한 것은 배선과 브리지의 신호 품질이다.

LED 깜빡임은 지웠다가 되살렸다. UART 가 안 나올 때 코드가 도는지 볼 최후
수단이 필요하다.

## 사다리 이후 과제 (2026-10-29)

최종 과제는 직접 짠 펌웨어로 도는 1000Hz 키보드다. TKL 키보드([devices/tkl-keyboard.md](../devices/tkl-keyboard.md))와
같은 칩이고, 나중에 하이스피드 USB 칩으로 8kHz 키보드를 만드는 징검다리다. TKL의 기본 펌웨어는 QMK + Vial을 유지하고,
직접 짠 펌웨어는 완성되면 TKL에 구워 QMK와 지연을 비교한다. 8단계 이후 계획(키 입력, 매트릭스 CPU·PIO 스캔, 키맵 저장,
USB, NKRO·지연 측정, 레이어)은 아직 문서 기준 제안이라 0~7처럼 단계표에 올리지 않았다. 아래 후보 표는 9월 기준이고,
그중 튜너·신스·오디오 인터페이스는 Seed3 이펙터와 겹쳐 뺐다.

## 사다리 이후 후보

7단계까지 끝난 뒤 만들 것의 후보다. 결정한 것은 없다. 어느 것이든 납땜이
필요하다.

| 후보 | 새로 다루는 것 | 확인된 제약 |
|---|---|---|
| MIDI 컨트롤러 | 키 매트릭스, 로터리 인코더, USB 디바이스 스택, USB MIDI 클래스 | 없음 |
| 튜너 | ADC 입력, 고정소수점 피치 검출 | 베이스 E1 41Hz, 5현 B0 31Hz라 한 주기가 24~32ms. 판정 창이 100ms 급으로 길어진다 |
| 자석축 매크로패드 | 홀센서 아날로그 키, 래피드 트리거 | ADC 12비트, ENOB 8.7. 채널 4개라 키 5개부터 아날로그 MUX 필요 |
| 신스 | PIO I2S 출력, 고정소수점 DSP | FPU 없음. SIO 하드웨어 보간기가 웨이브테이블 조회용 |
| USB 오디오 인터페이스 | UAC2 등시성 전송, I2S 입출력 | USB가 풀스피드(12Mbps). 2in/2out 48kHz 급이 상한 |

USB 클래스 장치(MIDI, 오디오 인터페이스)는 열거·컨트롤 전송·디스크립터를 다루는 USB
디바이스 스택이 먼저다. 이 트랙은 SDK를 링크하지 않으므로 그것을 직접 쓰게 되고, 후보
하나보다 큰 덩어리다. 사다리 8단계로 넣을지, 졸업 과제부터 pico-sdk와 TinyUSB를 허용할지는
정하지 않았다.

블루투스 송신은 독립 후보가 아니라 신스와 오디오 인터페이스의 출력 옵션이다.
RP2040 단독으로는 불가하고 외장 BT 오디오 모듈에 I2S로 넘기는 구조가 된다.
Pico W라면 BTstack의 A2DP source가 pico-examples에 있다(`a2dp_source_demo`,
pico-extras 필요). LDAC 인코딩은 RP2350에서 돌린 공개 프로젝트가 있고 그 프로젝트가
RP2040은 지원하지 않는다고 명시한다. 둘 다 문서 기준이고 보드도 없다. LDAC 송신은
[devices/ldac-dongle.md](../devices/ldac-dongle.md)의 PocketBeagle 2 트랙이 맡는다.

기각: 스트림덱 클론(단축키로 대체된다), 트랙볼.

순서 안은 MIDI 컨트롤러 → 튜너 → 자석축 매크로패드 → 신스 → 오디오 인터페이스다.
앞 것의 매트릭스·인코더·ADC 입력단이 다음 것에 그대로 쓰이도록 새로 다루는 것을
하나씩만 늘린다. 첫 후보인 MIDI 컨트롤러가 이 규칙에서 벗어나는 지점이 USB 스택이라,
위 결정이 순서보다 먼저다.
